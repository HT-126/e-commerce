pool:
    Opening a new connection to MySQL is slow (network, login, setup). A pool opens a few connections once and keeps them ready. When your code needs the database, it borrows one, uses it, and gives it back.

    Think of a taxi stand. Without a pool, every passenger calls a new taxi from far away. With a pool, taxis wait at the stand, and passengers take one and return it.

    Two more jobs of the pool:
        Limit: the pool has a maximum (for example 10). If 50 requests come at once, 40 wait in line. Without a limit, you could crash MySQL with too many connections.
        Many users at once: in Express, many requests run at the same time. Each one borrows its own connection.

    1. Why do we return the same message for a wrong email and a wrong password? And why run bcrypt.compare against a fake hash when the email does not exist?

            Kẻ tấn công: Dùng PUBLIC KEY (ai cũng biết) để ký token bằng HS256

    3. A review comment contains a malicious script and the page shows it without escaping (XSS). Why is that much more dangerous if the token is in localStorage than in an HttpOnly cookie?
        Token in localStorage: the script can read it with localStorage.getItem("token") and send it to the attacker’s server. The attacker then uses the token from their own computer, until it expires, even after the user closes the tab.
        Token in an HttpOnly cookie: JavaScript cannot read it at all. The script cannot take the token away. It can still send requests while the user’s tab is open (the browser adds the cookie), so XSS is still serious, but the attacker is stuck inside that one page and that one browser.

/********* Step 5: Rate limiting  ************/
    1. Why does the login limiter count only the FAILED tries (skipSuccessfulRequests: true), but the register limiter counts every request?
            Login: the attack is guessing, which means many failures. A successful login is not a threat. If we counted it, a real user who logs in often, or a whole office behind one IP, could be blocked for no reason.
            Register: the harmful event is the success. Every successful register writes a row to your database and costs about 0.25 s of CPU for the bcrypt hash. A script that makes thousands of fake accounts fills your table and slows the server. So here every request counts.

1. Why do we take userId from req.user.id and not from the request body? What could a bad user do if the body had a userId field?
    The cookie is signed by the server, so the user cannot change it. The body is just text that anyone can edit.     1. Why LIMIT 1 and ORDER BY position in the image subselect?
    A subselect used as a single value must return one row. If a product has 5 images and there is no LIMIT 1, MySQL stops with the error Subquery returns more than 1 row, and the whole cart returns 500. ORDER BY position makes sure the first image (the main one) is chosen. Without it, MySQL may return any image.

    2. Two things that go wrong if React does its own math:

    Old data. The price or the stock may have changed on the server. React would show a total that is no longer true, and a row that is now sold out would still look buyable.
    Different rules. The server has rules React may forget: max 10 per item, sold-out items are not in the total. Also, adding prices in JavaScript (0.1 + 0.2) gives small rounding errors. So the server is the one place that decides.z

    1. In the safe UPDATE, why is WHERE id = ? AND stock_quantity >= ? better than first running SELECT stock_quantity in JavaScript, checking if (stock >= qty), and then updating?
        With SELECT first and UPDATE later, there is a gap between the two. In the gap, another user can buy the same item, so your if (stock >= qty) uses old data. WHERE stock_quantity >= ? makes the check and the change one single step inside MySQL, which handles one request at a time on that row. So two buyers can never both take the last item.
